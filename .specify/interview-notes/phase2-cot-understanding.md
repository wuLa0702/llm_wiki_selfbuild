# Phase 2 理解笔记：为什么两步 CoT 而不是三步

> 记录时间：Phase 2 启动时
> 记录方式：用户口述，Claude 整理

---

## 核心问题：为什么拆分，为什么恰好是两步？

### 1. 为什么拆分

如果让大模型一步处理"读源文件 → 生成 wiki 页面"，它会倾向于：
- 遗漏非关键实体（只抓最明显的几个）
- 忽略与现有 wiki 的关联
- 跳过内容矛盾

**拆分本质**：让大模型"先计划，再执行"。

计划只管计划，执行只管执行。拆分后各阶段专注自己的任务，能力发挥更全面。

> 比方说原来一步只能发挥 90% 的功效，现在两步 1+1 > 95%。

### 2. 为什么不是三步或四步

**当前项目的数量级达不到那么大，两步已经够了。**

如果以后源文件数量多、复杂度高，可以扩展为三步：

| 步数 | 职责 |
|------|------|
| 第一步（计划） | 从关键词提取核心任务 |
| 第二步（规划） | 确定应该在哪些页面执行 |
| 第三步（执行） | 实际拆分执行 |

但现阶段不需要。

### 3. 未来扩展

当前的两步是写死的（analyze → generate）。后续可以设计为**可配置的 Pipeline**：

```python
# 未来可能的配置
PIPELINE_STEPS = [
    "analyze",     # Step 1: 分析提取
    "plan",        # Step 2: 规划页面
    "generate",    # Step 3: 生成页面
    "crosscheck",  # Step 4: 交叉校验
]
```

基于目前的开发阶段，不需要做到那么繁琐。**但在设计上预留扩展点是有价值的**——比如 `ingest()` 可以接受一个 `pipeline_steps` 参数。

## 面试怎么讲（用户自己的话）

> "我参考了 nashsu/llm_wiki 的两步 CoT 设计——把 ingest 拆成分析和生成两个阶段。核心思路是让 LLM 先计划再执行，计划只管计划，执行只管执行。拆分后各自专注，整体质量比一步到位提升了。为什么不是三步四步？因为目前项目的文档规模，两步已经足够。但我预留了扩展性，未来可以配置化为 N 步 Pipeline。"
