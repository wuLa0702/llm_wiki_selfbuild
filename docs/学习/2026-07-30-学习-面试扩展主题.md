### 1. Chunk 切分改进方案：向量索引从整页升级到章节级

**添加日期**：2026-07-30

#### 背景

当前向量搜索是整页编码（前 8000 字符），存在两个问题：
- 长页面尾部信息被截断丢失
- 一个页面讲多个概念时，向量模糊匹配导致检索精度低

BM25 已经在搜索时按 `##`/`###` 标题做章节级后处理，但向量搜索完全是页级的，两者不对称。

#### 面试回答（能直接讲的版本）

> 我们项目首版用整页编码，后期计划升级为 heading-based chunking。
>
> **怎么做的**：按 Markdown 的 `##`/`###` 标题切分 chunk，每个 chunk 约 600 字符，相邻 chunk 留 100 字符重叠防止边界概念丢失。每个 chunk 带上父标题链做上下文前缀，比如 `"Python > 数据类型 > 列表推导式\n\n内容..."`，再独立向量化入库。
>
> **检索时的关键设计**：向量搜索命中 chunk 后，不是把 chunk 直接返回给 Agent，而是按页面聚合——同一页面多个 chunk 命中取最高分加命中数加成，最终返回页面级结果，附上命中的章节标题和行号告诉 Agent "重点看这里"。Agent 仍然读完整页。
>
> **为什么这么设计**：Wiki 的核心理念是整页是完整知识单元，chunk 只做检索索引。如果直接返回 chunk 内容，就做成传统 RAG 了，丢掉了 Wiki 页面的可读性优势。BM25 侧不需要改，因为它已经有章节级后处理，只改向量侧就解决了核心问题。
>
> **增量更新**：页面修改后以 path 为前缀删掉旧 chunk，重新切分全量插入，简单可靠。不用语义切分是因为 Wiki 页面本身有标题结构，heading 切分零成本零调用，语义切分需要额外 LLM 调用属于过度工程。

#### 关键设计取舍速查

| 追问 | 回答要点 |
|------|---------|
| 为什么不直接把 chunk 返回给 Agent？ | Wiki 整页是完整知识单元，chunk 只做索引，返回 chunk 就做成传统 RAG 了 |
| BM25 为什么不跟着 chunk 化？ | BM25 已有章节后处理，效果够用，只改向量侧即可 |
| 怎么增量更新？ | 以 path 为前缀删旧 chunk，重新切分全量插入 |
| 为什么不用语义切分？ | Wiki 有标题结构，heading 切分零成本；语义切分需要调 LLM，过度工程 |
| chunk 大小怎么定的？ | 600 字符≈150-200 token，适配 all-MiniLM-L6-v2 的 256 token 上限留安全余量 |

#### 改动量估算

| 文件 | 内容 | 行数 |
|------|------|------|
| `chunker.py`（新建） | 标题解析 + 切分 + overlap | ~150 |
| `embedding.py`（修改） | chunk 级 embed/search/delete | ~80 |
| `engine.py`（修改） | 向量搜索改 chunk 级 + RRF 聚合 | ~60 |
| 其余 | ingest 流程 + 配置 + 测试 | ~150 |
| **合计** | | **~440 行** |
