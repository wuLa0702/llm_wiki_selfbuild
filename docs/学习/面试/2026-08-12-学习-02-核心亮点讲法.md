## 亮点 1：编译器模式 vs RAG（项目灵魂，必考）

**面试官问**："这个项目和传统 RAG 有什么区别？"

**30 秒讲法**：
> "我把它们比作编译器和解释器。RAG 是解释器——每次查询都是一次全新的解释执行：重新分块、重新检索、重新拼 prompt。而 LLM Wiki 是编译器——摄入时一次性编译成结构化知识，之后每次查询都是在这个已编译的知识层上导航。RAG 的知识是'临时拼凑'的，我的知识是'累积'的：第 100 篇文章的摄入会受益于前 99 篇已编译的知识，知识越用越厚。"

**追问接招**：
- Q：那编译错了怎么办？→ "三层兜底：raw/ 是不可变的事实基准，wiki 任何问题都能从 raw 重建；Lint 工具做质量检查，支持自动修复；摄入时 SHA256 缓存保证改了源文件才重编译。"
- Q：RAG 不是也能增量吗？→ "能，但 RAG 的检索质量依赖 chunk 切分和 embedding，知识之间没有显式关联；我的 wiki 页面通过 wikilink 形成知识图谱，查询可以做图谱扩展，这是 RAG 没有的结构化优势。"
- Q：为什么不干脆用 RAG？→ "这个项目定位是知识沉淀系统，不是问答机器人。对知识管理场景，编译一次多次查询的性价比远高于每次重新检索。"

## 亮点 2：两层 CoT 摄入（"先计划再执行"）

**面试官问**："你的摄入流程怎么设计的？为什么分两步？"

**30 秒讲法**：
> "摄入是'先计划、再执行'的两步 CoT。第一步让 LLM 只做分析——输出结构化 AnalysisOutput，包含页面拆分计划、实体识别、与现有 wiki 的关联判断；第二步才按计划生成页面。为什么拆两步：一步处理时模型会倾向于遗漏非关键实体、忽略与现有知识的关联、跳过内容矛盾。计划只管计划，执行只管执行。为什么不是三步：当前项目量级两步已经够了，但管道是可配置的，量级上去了可以扩。"

**追问接招**：
- Q：第一步失败了怎么办？→ "结构化输出重试一次；JSON 解析失败或重试仍失败，降级到单步 ingest_simple 模式，保证摄入闭环不中断——这是保底不阻塞的设计。"
- Q：token 成本怎么控制？→ "三个手段：SHA256 缓存（没改的源文件直接跳过）；注入 index-summary 而不是整个 index.md（省约 80% token）；每步都做 token 用量记录，落库可查。"
- Q：怎么保证生成页面质量？→ "frontmatter 强制注入 sources 溯源和 privacy 标记；页面类型限制在 7 类内（entity/concept/source/query/comparison/synthesis/overview）；写完后 Lint 工具做健康检查。"

## 亮点 3：手写 LangGraph + 三层自纠错（最硬的工程亮点）

**面试官问**："为什么不用 create_react_agent 要手写 StateGraph？"

**30 秒讲法**：
> "create_react_agent 给的是标准循环，但我的场景需要在循环的特定位置插入额外逻辑：工具调用前要校验（步数熔断、动作去重）、调用后要质检、质量差要 LLM 反思修正、有风险的工具要人工审批。手写 StateGraph 我才能精确控制这九条边的走向。而且手写意味着我对 add_messages reducer、conditional_edges、interrupt/Command 这些机制是真正理解的，不是调包。"

**面试官问**："自纠错具体怎么实现？"

**30 秒讲法**：
> "三层防御，从便宜到贵。第一层 validate_tool，纯代码零成本：步数熔断——超过 15 步强制收尾；动作去重——把工具调用规范化成 key（比如 search_wiki|查询词），同一动作重复执行直接拦下。第二层 verify_result，工具返回后检查输出质量：空返回、报错、格式异常都算失败。第三层 reflect_node 才动用 LLM：让模型用结构化输出判断 proceed 还是 revise，revise 时给出修正后的计划重新走。三层叠加后无效工具调用降低了约 60%。"

**追问接招**：
- Q：60% 怎么测出来的？→ 如实说："对比基线是裸 ReAct 在相同测试集上的工具调用次数，这个数字是开发期对比测出来的，具体测试集在测试目录里可以复现。"（**别虚报，能复现的数字才说**）
- Q：反思也是 LLM，不会引入新的错误吗？→ "会，所以反思只在第二层质检失败时才触发，是降级路径不是主路径；而且反思输出是结构化的（proceed/revise + revised_plan），不是自由发挥。成本上每次反思只多一次小模型调用。"
- Q：熔断 15 步怎么定的？→ "经验值 + 测试：正常问答链路最多 2-3 轮工具调用，15 步留了足够余量，同时把 LangGraph 的 recursion_limit 调到 150，避免框架默认 25 层先于我们的业务熔断触发。"

## 亮点 4：双轨记忆体系（Attention Sink + Working Memory）

**面试官问**："Agent 的记忆怎么设计的？"

**30 秒讲法**：
> "两条轨道，对应两类记忆需求。第一条是用户驱动的 Attention Sink：用户说'记住我叫 XX'、'我喜欢 XX'这类显式锚定，系统检测到后存入固定容量的 sink 池（15 个上限），带置信度衰减——每次对话衰减 0.05，低于 0.3 或闲置超 20 轮就淘汰；高频实体（≥3 次出现）自动锚定。它的特点是被摘要压缩时能存活，因为摘要生成时 sink 内容会作为上下文注入。第二条是系统驱动的工作记忆：5 个结构化槽位（用户身份/当前目标/关键事实/工具缓存/提及实体），用 reducer 做增量合并和去重。用户驱动的记忆回答'用户在意什么'，系统驱动的记忆回答'任务进行到哪'。"

**追问接招**：
- Q：摘要压缩怎么做？为什么不用官方方法？→ "对话超过 40 条非系统消息触发，用一个独立的小模型生成摘要（和主模型分开配额），用 RemoveMessage 删旧消息 + 摘要 SystemMessage 注入；摘要时同时注入 sink 和 WM 上下文，保证关键信息跨摘要存活。官方的 trimMessages/BaseStore 我们也评估过，但我们要的槽位合并和置信度衰减是自研的，所以核心逻辑手写。"
- Q：重启了记忆还在吗？→ "MemorySaver 管运行时，SQLite 管持久化。冷启动时从 SQLite 回灌消息 + sinks + WM，重建会话。"
- Q：记忆膨胀怎么办？→ "三个出口：摘要压缩、sink 淘汰机制、30 天归档降级——闲置超 30 天的会话用 LLM 生成归档摘要，不再保留完整消息，恢复时只回灌摘要。"

**追问接招（高难）**：Q：sink 置信度衰减和摘要冲突怎么办？
> "衰减是按对话轮次算的，摘要不改变轮次计数；sink 的排序优先级是置信度，摘要后注入上下文时取前 N 个。冲突场景我测试过：用户说'记住 A'，然后 30 轮没提 A，A 会自然衰减到淘汰——这符合'记忆会淡忘'的预期，反而是特性不是 bug。"

## 亮点 5：风险分级人工审批（Human-in-the-Loop）

**面试官问**："Agent 自主调用工具，安全怎么保证？"

**30 秒讲法**：
> "两个层面。第一个层面是工具本身的权限设计：Agent 只有 3 个只读工具——搜索、读页、查图谱，全部零副作用，所以大部分调用自动放行、不需要打断用户。第二个层面是风险分级审批：每个工具带 requires_approval 元数据，默认 fail-closed——只要没显式声明只读就默认需要审批；有风险的工具触发 LangGraph 的 interrupt() 挂起，前端收到 tool_approval_needed 事件，用户批准后用 Command(resume=approval) 恢复，拒绝则给模型返回拒绝消息让它改方案。审批是在图中间暂停，不是事后审计，这是关键区别。"

**追问接招**：
- Q：interrupt 和普通 tool call 在状态管理上有什么不同？→ "interrupt 会保存 checkpoint 并停止执行流，resume 时从暂停点继续，状态不丢；这是 LangGraph 的 checkpointer 能力，我们配合 MemorySaver 用的。审批期间会话不持久化新消息，避免状态不一致。"
- Q：以后加写工具怎么办？→ "注册表加一条元数据的事：requires_approval=True，审批节点自动接管，路由层不用改——这就是为什么把审批做成独立节点而不是散在工具里。"

## 亮点 6：混合检索（BM25 + 向量 + RRF）

**面试官问**："搜索怎么做的？"

**30 秒讲法**：
> "三种模式可切换：BM25 关键词检索（CJK Bigram 分词解决中文无空格分词问题，标题 3 倍加权），ChromaDB 384 维向量语义检索（all-MiniLM-L6-v2），hybrid 模式用 RRF 融合两个排序结果。为什么要融合：关键词召回准但漏语义，向量召回全但偶尔漂，RRF 取两个排名的倒数排名和，不需要调权重参数，鲁棒性最好。"

**追问接招**：
- Q：为什么是 384 维？→ "选型时对比过 OpenAI 的 1536 维和 MiniLM 的 384 维，本地模型隐私好、零 API 成本，384 维对 wiki 页面级检索的容量足够，还兼容 sentence-transformers 生态。"
- Q：向量搜索为什么默认关？→ "torch 依赖体积大（打包体积 + 内存），默认关、设置页可开，开启后检索失败自动回退 BM25——功能开关和降级路径都留着。"
- Q：有做 A/B 评估吗？→ "诚实回答：首版卡在'有比没有好'阶段，评估体系是规划的 Phase 5 内容。**别编**。"

## 亮点 7：安全模型（面试官常挖）

**面试官问**："你的系统有 Agent、有文件操作、有 LLM 输出，安全边界怎么设计？"

**30 秒讲法**：
> "四道边界。第一，目录隔离：raw/ 只读、wiki/ 可写、src/ 和 .claude/ 只读，Agent 永远碰不到代码和配置。第二，路径穿越防御：所有文件操作统一走 safe_path()——拒绝绝对路径、normpath 规范化后校验前缀，工具层和 API 路由共用这一个真源，没有第二套校验逻辑。第三，LLM 输出验证：文件名拒绝 ../，页面类型白名单（7 类），Markdown 内容禁止 script/iframe 注入。第四，隐私访问控制：restricted 标记的页面需要密码，bcrypt 哈希 + 24 小时 TTL bearer token。另外 Agent 工具全部只读，本身就是最粗的一条安全边界。"

**追问接招**：
- Q：LLM 输出如果绕过校验呢？→ "写入前校验 + 写入后 Lint 双保险；Lint 有静态和语义两档，自动修复有三策略（模糊匹配修正/建 stub/补缺失链接）。"
- Q：Prompt 注入防护呢？→ "诚实：当前 Wiki 内容来自用户自己的 raw 素材，属于受信边界内，注入面小；对外暴露后 Prompt 注入检测在规划里。这是 P1 缺口，主动讲比被问倒好。"

## 亮点 8：增量与性能（工程感加分项）

**面试官问**："数据量大了怎么办？性能怎么保证？"

**30 秒讲法**：
> "核心原则：全量 N² 的活不放在高频路径上，全部增量。三个实例：摄入走 SHA256 缓存，源文件没变直接跳过；知识图谱建图用内容签名缓存（所有 .md 的 rel-path+mtime 做 SHA256，签名没变就复用缓存图）；图谱关联度计算支持 target 子集增量计算而不是每次全量。启动时后台预热图谱，HTTP 立即可用。这个增量思路是从一次全量计算拖垮查询的教训里来的，项目笔记里记了根因。"

**追问接招**：
- Q：图谱是 N² 的？→ "相关度计算理论上全量是 N²，所以做了两件事：缓存签名短路 + compute_all 支持只算目标节点子集。社区发现用 Louvain 在 networkx 上跑，边多了可换启发式。"
- Q：并发呢？→ "SQLite 按调用建连接，写操作 commit；Windows 下清库用表级 DELETE 而不是删文件——删文件会因句柄占用失败且旧数据复活，这是踩过的坑。SSE 流式里同步 httpx 调用用 asyncio.to_thread 包，不阻塞事件循环。"

## 亮点 9：SSE 流式 + 前端闭环（完整工程）

**面试官问**："你的项目是完整的吗？前后端怎么通的？"

**30 秒讲法**：
> "完整闭环。前端 React 19 + Vite + shadcn/ui 九个页面，Chat 页通过 EventSource 消费后端的 SSE 流，5 种事件类型：token 逐字渲染、tool_start/tool_end 展示工具调用过程（用户看得到 Agent 在干什么）、done 带结构化回答和引用来源、error 兜底。多会话管理 + localStorage 持久化。后端 FastAPI 10 个路由模块，SQLite 16 张表，知识图谱前端用 vis-network 可视化，社区用不同颜色区分。"

**追问接招**：
- Q：为什么 SSE 不用 WebSocket？→ "单向流式输出场景 SSE 更简单：原生 EventSource、自动重连、HTTP 兼容性好；WebSocket 的双向能力这里用不到，Agent 输出不需要频繁上行。"
- Q：测试规模？→ "754 后端 pytest + 81 前端 + 22 E2E，LLM 全 mock，SQLite 用内存模式。"

## 亮点 10：MCP Server（踩在 2026 风口上）

**面试官问**："MCP 是什么？你项目里怎么用的？"

**30 秒讲法**：
> "MCP 是模型上下文协议，相当于 AI 世界的 USB-C 接口——工具按标准协议暴露，任何支持 MCP 的客户端（Claude Code、Cursor）都能即插即用。我用 @wiki_tool 装饰器暴露了 8 个 MCP 工具：search/read/list/graph/lint/stats/related/insights，支持 stdio 和 HTTP 双模式。这样外部 IDE 可以直接查询我的 Wiki 知识库。"

**追问接招**：
- Q：MCP 工具和 Agent 内部工具什么关系？→ "诚实讲：目前两套定义有重复，Agent 内部 3 个只读工具是 LangGraph 的 ToolNode 直接绑定的，MCP 8 个是独立装饰器注册的。文档里已列为待办——统一成 MCP-first 架构，Agent 内部工具也走 MCP 注册表，这是 P1 优化项。主动暴露这个设计瑕疵比藏着好。"
- Q：MCP 和 Function Calling 区别？→ "Function Calling 是模型 API 层的机制（模型决定调哪个函数），MCP 是工具分发的协议层（工具怎么被发现和调用）。MCP 解决的是'工具生态标准化'，Function Calling 解决的是'模型怎么用工具'。两者可以组合。"

## 亮点 11：知识图谱（差异化）

**面试官问**："知识图谱怎么构建的？有什么用？"

**30 秒讲法**：
> "从 wiki 页面的 wikilink 双向链接构建：正则解析所有 [[链接]]，两遍建图（收集文件 + 解析链接）。节点是页面，边是链接。然后做了三件事：一是 4-Signal 关联度——直接链接 ×3、同源文件 ×4（最强）、Adamic-Adar ×1.5、类型亲和 ×1.0，加权算出页面间的隐式关联；二是 Louvain 社区发现，把知识库自动分成主题社区；三是洞察引擎——跨社区惊喜连接、知识缺口（孤立节点/稀疏社区）自动发现，全部确定性实现、零 LLM 成本。查询时可以做图谱扩展：命中页面后沿边找邻居，回答更全面。"

**追问接招**：
- Q：为什么同源加权最高？→ "同一篇源文件编译出的页面天然共享主题上下文，这是知识溯源带来的强信号，比链接本身更可靠。"
- Q：洞察引擎的价值？→ "回答'你的知识库缺什么'——面试官问你怎么用 AI 发现问题，这就是 AI 在帮助维护知识库质量，不是只做问答。"
