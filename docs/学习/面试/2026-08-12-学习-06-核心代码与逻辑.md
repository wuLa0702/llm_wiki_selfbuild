## 🔴 P0 — 必背代码块

### #1 AgentState 状态定义（`src/agent/planning/graph.py:119`）

```python
class AgentState(TypedDict):
    """LangGraph 图共享状态"""
    messages: Annotated[list[BaseMessage], add_messages]   # 增量追加，非覆盖
    attention_sinks: list[dict]                            # 用户驱动长记忆
    working_memory: Annotated[dict[str, Any], working_memory_reducer]  # 系统驱动
    step_count: int                                        # 推理步数（熔断用）
    executed_actions: dict[str, Any]                       # 防重复哈希表
    self_correction: dict[str, Any]                        # 自纠错标记传递
    current_intent: dict[str, Any]                         # 意图分类结果
```

**逐段讲逻辑**：
- `messages` 用了 **Annotated + add_messages**——这是多轮会话的根基：每次节点返回新消息，LangGraph 按 reducer 追加而不是覆盖，Checkpointer 按 thread_id 持久化后，每轮只需传新消息。
- `working_memory` 用了**自定义 reducer**（见 #2）——说明 LangGraph 的 reducer 机制是通用的，业务字段可以自己写合并策略。
- `step_count` + `executed_actions` + `self_correction` 三个字段是自纠错的"基础设施"——熔断计数、防重复表、节点间信号传递。**面试官问"你的自纠错状态存在哪"，答这仨字段。**

**面试话术**：> "状态是一个 7 字段的 TypedDict。messages 用 LangGraph 官方的 add_messages 做增量追加，这是多轮隔离的基础；working_memory 我写了自己的 reducer 做槽位合并；另外三个字段是自纠错的——步数计数、动作去重表、修正标记。状态设计上，我把'对话内容'和'系统控制信息'分开，控制字段不进消息流，避免污染 LLM 上下文。"

### #2 working_memory_reducer（`src/agent/planning/graph.py:77`）

```python
def working_memory_reducer(old: dict | None, new: dict | None) -> dict:
    if new is None:
        return dict(old) if old else {}
    if old is None:
        return dict(new)
    merged = dict(old)
    for k, v in new.items():
        if not v and v not in (False, 0):
            continue  # skip None/empty
        if k == C.WM_SLOT_KEY_FACTS:          # 事实：dedup 追加 + 截断
            existing = merged.get(k, [])
            merged[k] = list(dict.fromkeys(existing + v))[:C.WM_MAX_FACTS]
        elif k == C.WM_SLOT_ENTITIES:         # 实体：同上
            existing = merged.get(k, [])
            merged[k] = list(dict.fromkeys(existing + v))[:C.WM_MAX_ENTITIES]
        elif k == C.WM_SLOT_TOOL_CACHE:       # 工具缓存：最新覆盖 + 截断
            existing = merged.get(k, {})
            merged_v = {**existing, **(v or {})}
            merged[k] = dict(list(merged_v.items())[:C.WM_MAX_TOOL_CACHE_ENTRIES])
        elif k == C.WM_SLOT_USER_IDENTITY:    # 身份：key 级合并
            merged[k] = {**merged.get(k, {}), **(v or {})}
        else:
            merged[k] = v
    return merged
```

**逐段讲逻辑**：
- reducer 的契约：`(旧值, 新值) → 合并值`，LangGraph 每次节点更新该字段时调用。
- **不同槽位不同策略**——这是设计的核心：事实/实体是"累积型"（dedup 追加 + 上限截断），工具缓存是"覆盖型"（最新覆盖），用户身份是"合并型"（key 级 merge 不互相覆盖）。
- `if not v and v not in (False, 0)`：跳过空值但保留布尔 False——防止合法 False 值被吞。

**面试话术**：> "工作记忆 5 个槽位语义不同，合并策略就不能一刀切：用户身份信息要保留用户自己的覆盖，事实列表要累积但防膨胀，工具缓存只需要最新。所以 reducer 按槽位分支。这个设计回答了一个问题——为什么不用 LangGraph 官方现成的 reducer？因为业务字段的合并语义是业务定的，框架给不了。"

### #3 图构建：节点 + 边（`src/agent/planning/graph.py:957`）

```python
builder = StateGraph(AgentState)
builder.add_node(C.NODE_INTENT_CLASSIFIER, intent_classifier_node)
builder.add_node(C.NODE_AGENT, call_model)
builder.add_node(C.NODE_EXTRACT_WM, extract_wm_node)
builder.add_node(C.NODE_WM_EVICTION, wm_eviction_node)
builder.add_node(C.NODE_VALIDATE_TOOL, validate_tool_node)   # ① 前置校验
builder.add_node(C.NODE_APPROVE, human_approval_node)
builder.add_node(C.NODE_TOOLS, tool_node)
builder.add_node(C.NODE_VERIFY_RESULT, verify_result_node)   # ② 后置验证
builder.add_node(C.NODE_REFLECT, reflect_node)               # ③ 推理反思
builder.add_node(C.NODE_SUMMARIZER, summarizer_node)
builder.set_entry_point(C.NODE_INTENT_CLASSIFIER)

builder.add_edge(C.NODE_INTENT_CLASSIFIER, C.NODE_AGENT)
builder.add_edge(C.NODE_AGENT, C.NODE_EXTRACT_WM)
builder.add_edge(C.NODE_EXTRACT_WM, C.NODE_WM_EVICTION)
builder.add_conditional_edges(C.NODE_WM_EVICTION, should_continue)      # 有无 tool_calls
builder.add_conditional_edges(C.NODE_VALIDATE_TOOL, should_after_validate)  # 熔断/重复/通过
builder.add_conditional_edges(C.NODE_APPROVE, should_after_approval)   # 批准/拒绝
builder.add_edge(C.NODE_TOOLS, C.NODE_VERIFY_RESULT)
builder.add_conditional_edges(C.NODE_VERIFY_RESULT, should_after_verify)   # 有效/反思
builder.add_edge(C.NODE_REFLECT, C.NODE_AGENT)
builder.add_edge(C.NODE_SUMMARIZER, END)

app = builder.compile(checkpointer=MemorySaver())
```

**逐段讲逻辑**：
- 节点名全部走 `constants.py` 常量（单一真源，改一处全局生效）。
- **4 条条件边是全部控制逻辑**：`should_continue`（有 tool_calls 走工具链，没有直接收尾）→ `should_after_validate`（熔断/去重拦截 vs 放行）→ `should_after_approval`（审批结果）→ `should_after_verify`（质检结果）。
- `tools → verify_result` 是**强制直连**不是条件边——工具输出必须过质检才能回 agent，这是"第二层防御不设跳过"的保证。
- `reflect_node → agent` 也是直连——反思后必回主循环重试。
- compile 时挂 `MemorySaver()`：checkpointer 是 interrupt/多轮/持久化的前提。

**面试话术**：> "图我手写而不是 create_react_agent，因为我的控制流是四段条件路由：意图分流、前置校验分流、审批分流、质检分流。这四段是 create_react_agent 给不了的。工具输出强制过质检节点，反思后强制回主循环——这些'强制'就是三层防御能成立的原因，因为路由图保证了它。"

### #4 会话编排三态（`src/agent/session.py:121`）

```python
config = {
    C.CONFIG_CONFIGURABLE: {C.CONFIG_THREAD_ID: thread_id},
    "recursion_limit": C.RECURSION_LIMIT,   # 必须显式设：默认 25 对本图太小
}
state_snapshot = agent.get_state(config)
if state_snapshot.interrupts:               # ① 审批恢复态
    stream_input = Command(resume=approval)
else:
    existing_messages = state_snapshot.values.get(C.STATE_MESSAGES, [])
    if existing_messages:                   # ② 续轮态：只传新消息
        input_messages = [HumanMessage(content=content)]
    else:
        persisted = M.load_thread(thread_id)  # ③ 冷启动/首轮：查 SQLite
        if persisted is None:                 # 首轮：注入 SYSTEM_PROMPT
            input_messages = [SystemMessage(content=SYSTEM_PROMPT), HumanMessage(content=content)]
        else:                                 # 冷启动恢复：回灌历史
            input_messages = deserialize_messages(persisted_msgs)
            input_messages.append(HumanMessage(content=content))
```

**逐段讲逻辑**：
- 入口先 `get_state(config)` 拿快照，**一个快照判断三种状态**：interrupt 挂起（审批）→ 续轮（MemorySaver 有历史）→ 冷启动（SQLite 有历史）/ 首轮（都没有）。
- 三态对应的输入构造完全不同：审批态用 `Command(resume=...)` 不传新消息；续轮只传一条 HumanMessage（add_messages 自动合并）；冷启动把序列化的历史消息反序列化回灌 + sinks + WM。
- `recursion_limit` 注释是真实踩坑：默认 25 对本图每轮 7-8 个节点只够 3.5 轮，会先于业务熔断触发——详见 08 踩坑 #1。

### #5 审批恢复（`src/agent/session.py:163`）

```python
state_snapshot = agent.get_state(config)
if state_snapshot.interrupts:
    if approval is None:
        yield error_event(ERROR_APPROVAL_REQUIRED)   # 挂起但没带审批 → 报错
        return
    if not isinstance(approval, dict):
        yield error_event(ERROR_APPROVAL_FORMAT)     # 格式校验
        return
    stream_input = Command(resume=approval)          # 恢复图执行
    input_messages = []                              # 恢复时不传新消息
```

**逐段讲逻辑**：
- 审批不是"对话里带个标记"，是**图真的暂停了**——interrupt() 在 approve 节点抛挂起，Checkpointer 保存现场。
- 恢复的唯一入口是 `Command(resume=approval)`，且**恢复时不能传新消息**（图从中断点继续，不是从头跑）。
- 两处防御：没带审批决策 → 直接 error 事件（不静默）；审批格式错误 → 报错（防脏数据进入 resume）。
