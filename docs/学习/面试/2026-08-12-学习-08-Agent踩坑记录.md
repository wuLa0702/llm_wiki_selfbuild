## 🔴 P0 — 面试必讲

### 坑 1：recursion_limit 默认 25 太小

**现象**：多轮对话跑到第 4 轮左右，LangGraph 抛 `GraphRecursionError`，明明业务熔断（MAX_STEPS=15）还没触发。

**根因**：LangGraph 的 recursion_limit 默认 25，按 **super-step（节点跳转）** 计数。本图每轮对话要走 7-8 个节点（intent → agent → extract_wm → wm_eviction → validate → approve → tools → verify → agent…），25 只够约 3.5 轮。框架默认值先于业务设计值触发。

**修复**（`src/agent/session.py` config）：
```python
config = {
    C.CONFIG_CONFIGURABLE: {C.CONFIG_THREAD_ID: thread_id},
    "recursion_limit": C.RECURSION_LIMIT,   # = 150，注释写明原因
}
```
150 = 业务熔断 15 步 × 每步约 8 节点 × 1.25 余量，保证**业务熔断永远先触发**。

**面试 30 秒故事**：
> "遇到过一个和'框架默认值'相关的坑。LangGraph 的 recursion_limit 默认 25，按节点跳转次数计数，而我的图每轮对话要经过 7-8 个节点，所以第 4 轮就会撞框架限制——比我设计的业务熔断（15 步）还早。修复是把 recursion_limit 显式设成 150：业务熔断 15 步 × 每步 8 节点 × 余量。这个坑的教训是：框架默认值是给通用场景的，用了自定义循环必须重新算这个数。代码里注释写明了推导过程，防止后人改回去。"

### 坑 2：Windows 事件循环阻塞（同步 httpx 混入 async）

**现象**：SSE 流式对话在 Windows 上偶发**整个进程卡死/崩溃**，Linux 上稳定复现不出。

**根因**：`with_structured_output` 内部是**同步 httpx 调用**。在 async 事件循环里直接调用同步网络请求，阻塞事件循环；Windows 的 ProactorEventLoop 被阻塞后行为更糟，可能导致进程崩溃。

**修复**（`src/agent/session.py:306`，注释原文）：
```python
# with_structured_output 内部是同步 httpx 调用，必须放到线程池
# 否则阻塞 asyncio 事件循环，在 Windows 上可能导致进程崩溃
structured = await asyncio.to_thread(format_response, str(m.content))
```
同类修复：意图分类 `asyncio.to_thread(classify_intent, content)`。

**面试 30 秒故事**：
> "一个平台相关的坑：结构化输出提取用的是同步 httpx，在 async 流式上下文里直接调，Linux 上只是慢，Windows 上直接崩进程。排查时先看调用链，发现 LangChain 的 with_structured_output 内部是同步实现，就统一用 asyncio.to_thread 把同步 LLM 调用包进线程池。教训：用 LangChain 在 async 项目里，**同步实现混进事件循环是必踩的坑**，要建立'所有同步网络调用必须 to_thread'的纪律。"

### 坑 3：interrupt 挂起后状态机误用

**现象**：审批挂起期间收到新消息 / 前端没带审批决策就 resume → 状态错乱或报错。

**根因**：图在 approve 节点 `interrupt()` 暂停后，**只接受 `Command(resume=approval)`**，不接受新消息；且 resume 必须有合法的审批决策，否则 LangGraph 行为未定义。

**修复**（`src/agent/session.py:163`）：
```python
state_snapshot = agent.get_state(config)
if state_snapshot.interrupts:
    if approval is None:            # 挂起但没带审批 → 明确报错
        yield error(EVENT_ERROR, ERROR_APPROVAL_REQUIRED); return
    if not isinstance(approval, dict):  # 格式校验
        yield error(EVENT_ERROR, ERROR_APPROVAL_FORMAT); return
    stream_input = Command(resume=approval)
    input_messages = []             # 恢复时不传新消息
```

**面试 30 秒故事**：
> "HITL 的坑在状态机严谨性。interrupt 挂起后，图只认 Command(resume)，此时如果客户端又发来新消息，或者 resume 没带审批决策，状态就脏了。我在入口用 get_state 快照检测 interrupts，然后两道防御：没带审批直接返回错误事件而不是静默，审批格式校验。关键设计是恢复时不传新消息——图是从中断点继续的，不是从头跑。这个严谨性在线上是必须的，因为前端各种异常路径都会打到后端。"

## 🟠 P1 — 高频故事

### 坑 4：MemorySaver 同 thread 冲突

**现象**：`/v1/agent/threads/{id}/regenerate`（重新生成回答）和原会话共用 thread_id，MemorySaver checkpoint 互相覆盖，生成结果串味。

**根因**：MemorySaver 按 config 中的 thread_id 索引 checkpoint；regenerate 若复用原 thread_id，会读取/写入同一个 checkpoint，和正常对话流冲突。

**修复**：regenerate 时用 `{thread_id}_reg` 作为独立 config，跑完单独持久化，不污染原会话的 MemorySaver 状态。

**面试 30 秒故事**：
> "多会话隔离的坑：regenerate 功能如果复用原 thread_id，MemorySaver 的 checkpoint 就撞了——重生成和正常对话写同一个状态。修复是给 regenerate 用独立的 config 后缀（thread_id_reg），各跑各的 checkpoint，结果单独持久化。这个坑说明了 checkpointer 的隔离粒度：**隔离的单位是 config 不是会话**，任何功能想独立跑状态都要有自己的 config。"

### 坑 5：FTS5 对中文匹配差

**现象**：对话全文搜索（FTS5）搜中文关键词命中率低，搜英文正常。

**根因**：FTS5 默认分词器按空格/标点切词，中文没有空格，整句被当成一个 token，子串匹配不上。

**修复**（`src/agent/memory/store.py`）：CJK 感知——检测查询含中文时降级用 `LIKE '%kw%'` 模糊匹配，英文走 FTS5 的 MATCH。`search_conversations()` 内部分流。

**面试 30 秒故事**：
> "中文本地化坑：FTS5 全文索引对中文基本失效——默认分词按空格切，中文整句一个 token，子串搜不到。修法是查询侧分流：含 CJK 字符走 LIKE 模糊匹配，纯英文走 FTS5 MATCH。也评估过 jieba 分词 + 自定义 tokenizer，但 FTS5 自定义 tokenizer 在 Python 里集成成本高，LIKE 对个人项目的数据量完全够用——这是成本收益的取舍，不是不会做。"

### 坑 6：旧摘要残留

**现象**：摘要压缩后，被 RemoveMessage 标记删除的旧消息在部分场景仍出现在上下文里，摘要重复注入。

**根因**：summarizer 节点返回 RemoveMessage + 摘要 SystemMessage，但某些分支（如 reflect_node 修正后重入）的路径上消息列表状态没有同步清理，旧摘要叠加。

**状态**：devlog 记录为 P3 已知 bug（当时已确认未修），后续版本需验证是否已修复。**面试讲这个坑时先说结论**："已知的边界 case，当时的处理是记录在案 + 定级 P3 低优，因为触发路径窄（反思重入 + 摘要同轮）。"

**面试 30 秒故事**：
> "状态清理的坑：摘要压缩用 RemoveMessage 删旧消息，但反思重入的路径上摘要会重复注入——RemoveMessage 在条件路由分支上没生效完整。当时定级 P3：触发条件窄（反思和摘要同一轮），不影响主流程，记录在案排期修。讲这个坑的价值在于：**不是所有 bug 都要立刻修，分级决策本身也是工程能力**。面试官要听的是你怎么判断优先级。"

### 坑 7：LLM 超时 15s 太短

**现象**：大文件生成页面 / 长对话摘要调用 LLM 频繁超时，`max_retries=1` 重试后依然失败。

**根因**：`ChatOpenAI(timeout=15, max_retries=1)`——单次 15s 对长 prompt 生成不够，重试一次共 30s 也没用（重试的是同一个会超时的调用）。

**修复**：`timeout=15 → 120, max_retries=1 → 0`——一次最长等 2 分钟，不重试。**重试策略在调用方设计**（如 WikiCompiler 两步 CoT 的"重试 1 次 + 降级"），而不是 SDK 层盲目重试。

**面试 30 秒故事**：
> "超时参数坑：最初 timeout=15 + 重试 1 次，大 prompt 生成要 20-30 秒，重试也救不回来。改成 timeout=120 + 不重试，把重试策略上移到调用方——业务层知道什么时候值得重试（两步 CoT 分析失败重试一次），SDK 层盲目重试只是浪费钱。教训：**超时和重试是业务策略不是库配置**，要按操作类型分别定。"

## 🟡 P2 — 备选故事

### 坑 8：SQLite 跨线程

**现象**：多线程请求下 SQLite 报 `SQLite objects created in a thread can only be used in that same thread`。

**修复**：模块级单例连接 + `check_same_thread=False`，并发写靠 SQLite 自身的锁 + 写操作即时 commit。

**面试一句话**：> "SQLite 默认连接绑线程，Agent 层多线程调用会炸。单例连接开 check_same_thread=False，短事务 + 即时 commit，个人项目量级下这是够用且简单的方案。"

### 坑 9：wikilink 裸名断链

**现象**：LLM 生成 wikilink 用裸名（`[[毕木]]`），断链检测用完整路径（`entities/毕木.md`），165 个链接被误报断链，一键修复还把有效链接全删了。

**修复**：源头方案——prompt 强制 LLM 生成 `[[目录/文件名.md]]` 完整路径；lint 修复改三层策略（模糊修正 → 建 stub → 补缺失），不再一刀切删除。

**面试一句话**：> "LLM 输出规范和校验逻辑不一致会互相误伤。修法是源头约束——prompt 里强制完整路径格式，而不是在 lint 侧打补丁。这个坑也教会我：**LLM 生成物的规范要靠提示词约束 + 校验双保险，且修复策略要有区分度，不能一刀切**。"

### 坑 10：同步 LLM 调用混入 async（变体）

**现象**：意图分类在流式输出前同步执行，首次对话首 token 延迟高。

**修复**：`asyncio.to_thread` 包裹（同坑 2），且意图分类失败非阻断（降级 unknown 继续）。

**面试一句话**：> "同类问题第二例：意图分类也是同步实现，包 to_thread + 失败降级不阻断。一个坑出现两次就要立纪律——我把'同步网络调用必须 to_thread'写进了代码注释和规范。"

## 面试故事组织模板（任何一个坑都按这个讲）

1. **现象**（30 秒）：什么场景、什么报错、影响面多大——**要有细节，细节=真实**
2. **排查**（30 秒）：怎么定位的——看日志/看调用链/二分法/平台差异复现
3. **根因**（30 秒）：一句话说透本质，**别停在表面现象**
4. **修复**（30 秒）：改了什么、为什么这么改、有没有更优方案被否掉
5. **沉淀**（15 秒）：这个坑沉淀成什么纪律/注释/规范

> 2026 面试行情：**"具体改了什么逻辑、提升多少百分比"答不出来的直接扣分**。每个故事的数字和文件行号都要能指到仓库。
