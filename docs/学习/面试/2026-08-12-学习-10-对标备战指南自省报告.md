## 0. 对标方法声明（为什么不能照搬）

指南的项目选型是**「多 Agent 行业研究系统」**，本项目的定位是**「单 Agent 知识编译系统」（LLM Wiki）**。功能不同，对标必须分三类处理：

| 对标类型 | 含义 | 本项目对应 |
|---------|------|-----------|
| ✅ 达标 | 指南要求的能力已具备且能讲 | 容错、成本、安全（大部分） |
| ❌ 缺口 | 指南要求的能力缺失或讲不透 | 评估体系、HITL 的两个场景、预算控制 |
| ➖ 不适用 | 因项目定位差异，指南要求与本项目冲突 | 多 Agent、RAG 评估口径（本项目是编译器模式） |

**自省核心结论**：本项目不缺"能讲的东西"，缺的是**证明"有效"的系统化证据**和**两个 HITL 场景**。指南"讲透一个点 > 浅尝十个点"的原则下，本项目的"单 Agent 做深"路线是站得住的，但要补上效果层的证据链。

## 1. 五大模块逐项对标（指南 §3.2）

### 1.1 评估体系 — ❌ 最大缺口（指南 P0）

| 指南要求 | 本项目现状 | 自省 |
|---------|-----------|------|
| 准确率/召回率指标 | 有测试（754 后端 + 81 前端 + 22 E2E），但**测试 ≠ Agent 效果评估** | 测试证明"没写错"，不证明"答得好" |
| 人工评估 | lint 工具做页面质量检查（健康检查） | 只覆盖 wiki 页面产物，不覆盖**回答质量** |
| bad case 分析 | 08 文档有 10 个踩坑（开发期），无**运行期 bad case 沉淀机制** | 踩坑故事可讲，但缺"上线后效果数据" |
| 效果对比数据 | 三层自纠错有"无效工具调用降 ~60%"（对比裸 ReAct，开发期测得） | ✅ 唯一拿得出手的效果数字，但只有这一个 |

**行动项**：
- P0：做一份**评估用例集 + 跑分记录**（20-30 条真实问答，记录：回答质量分档 / 工具调用次数 / 自纠错触发次数），落成 `docs/agent-evaluation.md`
- P0：60% 的复现方法写成文档（测试集路径 + 对比基线），面试被问"怎么测的"能当场指路
- P1：bad case 收集入口（会话里标记"回答不满意"→ 落库可查）

### 1.2 HITL 机制 — ⚠️ 半达标（指南 P0，四个场景做两个）

| 场景 | 本项目现状 | 结论 |
|------|-----------|------|
| 高风险审批 | ✅ **已做且做得深**：风险分级 + interrupt 挂起 + Command(resume) 恢复，默认 fail-closed（`src/agent/action/registry.py`） | 达标，02 亮点 5 话术已备 |
| 需求澄清 | ❌ 只有**用户追问**的识别（intent.py `_match_clarification`），无**Agent 主动停下问用户** | 缺口 |
| 中途确认 | ➖ 与需求澄清同属"停下来问人"，未做 | 缺口 |
| 输出审核 | ⚠️ verify_result 是**代码质检**（空/错误检测），不是人工审核 | 部分达标（可讲成"自动化质检 + 人工审批"组合） |

**行动项**：
- P0：在 agent 图中加**澄清节点**（意图识别为"目标不明确"时，先回问确认再进搜索循环）——这是小改动，但补全了 HITL 两个场景的硬要求
- P1：若不加节点，面试话术改为"高风险审批 + 自动化质检"两个场景（也能站住，但不如补上硬气）

### 1.3 容错处理 — ✅ 达标（指南 P1，本项目强项）

| 指南要求 | 本项目现状 |
|---------|-----------|
| 工具调用失败重试 | ✅ LLM 调用重试 + 超时参数按规模调整（120s/0 重试，踩过 15s 吞调用的坑） |
| 降级策略 | ✅ ingest 失败降级 ingest_simple 保闭环；搜索向量关闭自动 BM25 兜底 |
| 超时处理 | ✅ 同上 |
| 异常兜底 | ✅ 三层自纠错（熔断≤15 步 / 动作去重 / 质检 / LLM 反思）+ 单实例锁崩溃兜底 |

**自省**：这是本项目最能打的模块，远超市面均值。面试时是**主攻方向**，但要防一个坑——别一次全倒出来，按追问链一层层给。

### 1.4 成本控制 — ✅ 基本达标（指南 P1）

| 指南要求 | 本项目现状 |
|---------|-----------|
| Token 用量统计 | ✅ `src/core/token_tracker.py`：内存汇聚 + SQLite 持久化 + 当日/周汇总 |
| 模型分级 | ✅ DeepSeek Flash 主 + Pro 兜底（评分矩阵，成本差 12 倍） |
| 缓存策略 | ✅ SHA256 摄入缓存 + index-summary 注入省 ~80% token |
| 预算控制 | ❌ 有**费用估算**（`pricing.py` 动态价格），无**预算上限/超限熔断** |

**行动项**：
- P2：预算上限是锦上添花（设置页配月预算，超限暂停 LLM 调用），面试可诚实讲"统计有、控制无，是下一步"

### 1.5 安全机制 — ✅ 基本达标（指南 P2）

| 指南要求 | 本项目现状 |
|---------|-----------|
| Prompt 注入防护 | ⚠️ raw/ 是用户自己的素材（信任边界内），无显式注入检测——**要能讲"为什么"** |
| 数据脱敏 | ✅ privacy 检测 + restricted frontmatter 门禁（生成全量、按标记门禁） |
| 权限控制 | ✅ 页面密码验证（bcrypt）+ 路径安全唯一真源（safe_path 防穿越） |
| 审计日志 | ✅ operation_log 表 |

**行动项**：
- P2：准备一句话："注入防护为什么没做——raw/ 是可信输入（用户自放），风险面在输出展示层（Markdown 渲染已做脚本过滤），真要防注入会在摄取时加检测"

## 2. 项目选型差异自省（指南 §3.1 对照）

指南选"多 Agent"的理由是**覆盖面广**（RAG/工具/Memory/多 Agent/评估全都能放）。本项目功能不同，逐项对照：

| 指南覆盖点 | 本项目对应 | 差异结论 |
|-----------|-----------|---------|
| RAG | **编译器模式**（反 RAG 定位） | ➖ 不适用——这是本项目的**差异化灵魂**，面试必考且话术已备（02 亮点 1） |
| 工具调用 | ✅ 3 只读工具 + MCP 8 工具（stdio/HTTP 双模式） | 达标 |
| Memory | ✅ 双轨记忆（Sink + WM）+ 摘要压缩 + SQLite 持久化 | **超纲**，比指南要求更深 |
| 多 Agent | ❌ 单 Agent 边界明确 | ➖ 不适用——指南说"一个讲得透的好项目 > 背八股"，单 Agent 做深同样成立；但要备好"为什么不做多 Agent + 下一步怎么规划"（01 决策 13 已备） |
| 评估 | ❌ 缺系统化评估（见 §1.1） | **真实缺口**，与指南一致 |

**自省结论**：选型差异不是缺陷——"编译器 vs RAG"和"手写 StateGraph"是比"多 Agent 全家桶"更稀缺的差异点。但要补两件事：①评估体系（两项目都缺，必须补）；②多 Agent 的"不做"要讲得理直气壮且有规划。

## 3. 追问链 5 层自查（指南 §3.3）

| 层 | 指南问题方向 | 本项目准备度 | 缺口 |
|----|------------|------------|------|
| 1 业务层 | 解决什么问题 / 用户是谁 / 为什么用 Agent | ✅ 01 §8 电梯陈述 + 02 亮点 1 | 无 |
| 2 架构层 | 整体架构 / 为什么这么拆 / 对比过什么 | ✅ 01 §2 架构图 + §5 15 个决策 | 无（注意：手写 LangGraph 会被深挖，06 文档已备代码逐段） |
| 3 实现层 | RAG / 工具 / 记忆 / 协作 / 坑 | ✅ 02 亮点 2-5 + 08 踩坑 | 无 |
| 4 效果层 | 怎么评估 / 提升多少 / 怎么证明 / bad case | ⚠️ 只有"60% 无效调用降低"一个数字 | **最大缺口**：无回答质量指标、无 bad case 数据 |
| 5 优化层 | 还有什么不足 / 下一步 / 成本 / 安全 | ✅ 01 §7 缺口表（诚实分） | 无（预算控制可加进"不足"清单） |

**行动项**：补 §1.1 的评估用例集后，第 4 层就从"只有一个数字"变成"有指标、有用例、有 bad case"。

## 6. 结论一句话

> 本项目对标指南后：**容错、成本、安全、深度都超纲，灵魂层（编译器模式 + 手写图）比指南选型更稀缺**；真实缺口只有两个——**评估体系（效果层证据链）和 HITL 需求澄清场景**。补完这两个，项目就是"单 Agent 做深"路线的完整闭环。
