## 项目介绍

### 总体概述

基于 Karpathy LLM Wiki 理念的"知识编译 + 智能问答"系统：用户把原始资料放入 `raw/sources/`，系统调用 LLM 将资料**一次性编译**为结构化 Wiki 知识页面（`wiki/` 目录，Markdown + YAML frontmatter），并维护知识图谱与元数据库；查询时由一个 LangGraph Agent 基于已编译的知识层回答。与 RAG 每次查询重新分块检索不同，本项目编译一次、查询多次，知识随使用累积。

系统为完整全栈闭环：摄入（Ingest）→ 知识图谱（Graph）→ 混合检索（Search）→ Agent 对话（Chat，SSE 流式）→ React 前端 → 桌面打包。核心逻辑全部自研（手写 LangGraph 状态机），LLM 调用走统一适配层。

### 技术栈

| 层 | 技术 | 用途 |
|----|------|------|
| 后端框架 | Python 3.11 · FastAPI | REST API（/v1/ 前缀）+ SSE 流式 |
| Agent | LangGraph / LangChain | 手写 StateGraph 状态机 + LLM 封装 |
| 存储 | SQLite（wiki.db + agent_persistence.db） | 页面元数据（16 表）+ 会话持久化 |
| 知识文件 | Markdown + YAML frontmatter | wiki/ 知识层 · raw/ 素材层（只读） |
| 检索 | 自研 BM25（CJK Bigram）+ ChromaDB（384-dim 向量，默认关闭） | 双路召回 + RRF 融合 |
| LLM | DeepSeek（V4 Flash 主 / Pro 兜底，LLMAdapter 可换 Provider） | 摄入编译 + Agent 推理 |
| 前端 | React 19 + Vite + TypeScript + Tailwind CSS + HeroUI | 九页面 SPA |
| 协议 | SSE（5 事件）· MCP（stdio/HTTP 双模式，8 工具） | 流式对话 + 外部工具接入 |
| 打包 | PyInstaller（单文件 exe，run.py 入口） | 桌面应用分发 |

## 功能 1：摄入（Ingest）【示例已审批】

**功能**：把 `raw/sources/` 下的原始素材文件，交给 LLM 处理，生成 `wiki/` 下的结构化知识页面（Markdown + YAML frontmatter），并把页面元数据（标题、类型、标签、字数、链接关系）写入 SQLite。

**如何实现（是什么）**：
- 入口：`WikiCompiler.ingest()`（`src/core/compiler/wiki_compiler.py`）
- 流程：SHA256 缓存检查 → 读文件 + 隐私检测 + 截断保护 → 注入 index-summary 上下文 → 分析步（`chat_structured` 结构化输出）→ 生成步（`---PAGE:path---` 分块模板输出）→ 写页面（注入 frontmatter + DB upsert + 记录 wikilinks）→ 更新导航文件（index/overview/log）→ 触发图谱重建 → 记录 token 用量
- 数据结构：`wiki_pages` 表（path/title/page_type/tags/created_at/updated_at/word_count）· `page_links` 表（source_path/target_path）· `ingest_cache` 表（source_path/sha256_hash/ingested_at）

**过程方法（为什么）**：
- **拆两步**：对比过单步一次生成——单步时 LLM 倾向遗漏非关键实体、忽略与现有知识关联、跳过内容矛盾；拆成"先计划、后执行"后每步职责单一。量级上来后可配置扩展为 N 步管道
- **失败降级**：分析步失败重试 1 次，仍失败降级单步 `ingest_simple` 模式——对比"直接报错中断"方案，选降级是为了保证摄入闭环不中断
- **缓存**：源文件 SHA256 比对，未变更跳过——对比"全量重编译"，选缓存是遵循高频路径增量优先原则
- **上下文控制**：注入 index-summary 而非整个 index.md——对比全量注入，省 token 且减少无关上下文干扰

**踩坑**：
- **165 个断链误报**
  - 现象：LLM 生成的 `[[xxx]]` 链接不带完整路径，lint 检查全部误报
  - 根因：prompt 未约束路径格式，LLM 习惯用裸名
  - 解决：prompt 前置约束"引用的 `[[path]]` 必须是本次实际创建的页面"，源头解决
  - 教训：生成类问题优先从 prompt 源头约束，不要靠后处理兜底
- **一键修复误杀 165 个有效链接**
  - 现象：`lint/fix` 直接删除 165 个链接，把格式不匹配但内容有效的链接也删了
  - 根因：破坏性修复逻辑没分级，删除是第一选项
  - 解决：破坏性自动修复分级（建议修正 → 存根 → 补充），删除不是第一选项
  - 教训：破坏性自动操作必须先分级评估，误删的恢复成本远高于多一步确认
- **15s 超时吞掉 52KB 源文件的生成调用**
  - 现象：大源文件摄入时调用失败，重试也失败
  - 根因：LLM 调用用框架默认超时（15s）+ 1 次重试，52KB 源文件的生成超出预算
  - 解决：按 prompt 规模调整（120s / 0 重试），一次成功
  - 教训：LLM 调用超时要按输入规模估算，别用框架默认值

**数据**：
- token 节省约 80%：**设计估算**（基于 index-summary 注入与全量 index 的 token 对比测算），未用生产数据复核
- 缓存命中率：**无相关数据**（`ingest_cache` 表存在，未实测命中率统计）
- 平均摄入速度：**无相关数据**
- 说明：当前本地 wiki.db 与 %APPDATA%/LLM-Wiki/wiki.db 均为空测试库（wiki_pages 0 条），**项目尚无生产级业务数据**

**证据**：`src/core/compiler/wiki_compiler.py` · `src/core/cache.py` · `src/db/repository.py` · `src/core/token_tracker.py` · `.learnings/interview-notes.md` · `tests/test_core/`

## 功能 2：查询 / 检索（Query / Search）

**功能**：对知识库提供两类查询入口——`/v1/query`（查询引擎，图谱扩展 + 检索命中页面）与 `/v1/search`（搜索页，关键词/向量/混合三模式）。搜索支持分页（k+1 游标）。

**如何实现（是什么）**：
- 入口：`src/api/routes/misc.py`（/v1/search）· `src/tools/search_tool.py`（SearchTool）· `src/core/embedding.py`（EmbeddingEngine）
- BM25：自研实现，CJK Bigram 分词（中文相邻两字为词）+ 标题加权 + Okapi 公式
- 向量：ChromaDB 384 维（all-MiniLM-L6-v2），受 `embedding_enabled` 配置控制，**默认关闭**；关闭时自动回退 BM25
- 混合：双路召回结果用 RRF（Reciprocal Rank Fusion）融合排序，免调参

**过程方法（为什么）**：
- **BM25 自研而非用库**：中文分词没有现成好用的轻量方案（jieba 依赖重），Bigram 对个人项目数据量够用且零外部依赖
- **向量默认关闭**：torch/embedding 依赖体积大，最小部署集优先；架构留开关（设置页可启），关闭时 BM25 兜底不破坏体验
- **RRF 而非加权求和**：免调参，两路分数尺度不同时加权和需要调权重，RRF 只比排名

**踩坑**：无专属坑（搜索相关坑见"记忆系统"的 FTS5 中文匹配）。

**数据**：
- 检索准确率/召回率：**无相关数据**（未做评测集）
- 向量检索命中率：**无相关数据**（默认关闭状态）

**证据**：`src/tools/search_tool.py` · `src/core/embedding.py` · `src/api/routes/misc.py`

## 功能 3：知识图谱（Graph）

**功能**：基于页面间 wikilink 构建知识图谱，提供：4-Signal 关联度计算、Louvain 社区发现、洞察引擎（惊喜连接 / 知识缺口自动发现）。图谱用于查询时扩展相关页面、图谱页可视化、洞察展示。

**如何实现（是什么）**：
- 数据：`graph_relevance` 表（source_path/target_path/total_score/direct_link/source_overlap/adamic_adar/type_affinity）
- 4-Signal：直接链接（direct_link）、源重叠（source_overlap）、Adamic-Adar 邻居相似度、类型亲和（type_affinity），加权合成 total_score
- 社区：Louvain 算法社区划分
- 洞察：惊喜连接（关联度高但无直接链接的页面对）、知识缺口自动发现
- 增量：图谱签名缓存 + relevance 增量计算（只算新增节点，不全量重算）

**过程方法（为什么）**：
- **4-Signal 而非单一信号**：直接链接不够——两个页面无直接链接但共享多个来源，也应有关联；多信号加权是"多种证据交叉"
- **增量优先**：对比过全量 N² 计算——全量重算把摄入链路拖到不可接受；改为只算新增节点（O(N²) → O(N×M)），全量计算放低频（手动/定时）

**踩坑**：
- **全量关联度计算撑爆性能**
  - 现象：每次摄入后全量重算所有页面两两关联度，页面多时耗时爆炸
  - 根因：O(N²) 全量计算放在高频路径（摄入触发）
  - 解决：改为增量——只算涉及新增节点的对，签名缓存跳过未变化子图
  - 教训：算法必须先问调用频率，全量 N² 永远不要放高频路径

**数据**：
- 图谱节点/边规模：**无相关数据**（空库）
- 社区数量：**无相关数据**
- 增量 vs 全量耗时对比：**无相关数据**（教训来自开发期实测，未留数字）

**证据**：`src/core/graph/graph.py` · `src/core/graph/community.py` · `src/core/graph/insights.py` · `src/db/repository.py`（save_relevance/get_related_pages）

## 功能 4：Agent 对话（LangGraph 状态机 / 自纠错 / 审批）

**功能**：基于手写 LangGraph StateGraph 的 ReAct Agent，通过 SSE 流式回答用户问题。图拓扑 9 节点 + 4 条条件边，支持多轮会话、三层自纠错、风险分级人工审批、意图分类、会话持久化。

**如何实现（是什么）**：
- 状态：`AgentState` TypedDict 7 字段（`src/agent/planning/graph.py`）——messages（add_messages 增量追加）、attention_sinks、working_memory（自定义 reducer）、step_count、executed_actions、self_correction、current_intent
- 图拓扑：intent_classifier → agent → extract_wm → wm_eviction →（条件）validate_tool → approve → tools → verify_result →（条件）reflect_node → agent … → summarizer → END
- 4 条条件边：should_continue（有无 tool_calls）、should_after_validate（熔断/重复/放行）、should_after_approval（批准/拒绝）、should_after_verify（质检/反思）
- 三层自纠错：L1 validate_tool（MAX_STEPS=15 熔断 + 动作规范化去重，纯代码）→ L2 verify_result（工具输出质检：空/错误检测）→ L3 reflect_node（LLM 结构化输出 proceed/revise + 修正计划）
- 风险分级审批：工具注册表 `ToolDefinition` 带 `requires_approval` 元数据；有风险工具在 approve 节点 `interrupt()` 挂起，前端收到 tool_approval_needed 事件，用户批准后 `Command(resume=approval)` 恢复；默认 fail-closed（未显式声明只读即需审批）
- 会话三态（`src/agent/session.py`）：`get_state` 快照一次判断——审批恢复态（interrupts 存在 → Command(resume)，不传新消息）/ 续轮态（MemorySaver 有历史 → 只传新消息）/ 冷启动态（SQLite 有历史 → 反序列化回灌）/ 首轮（注入 SYSTEM_PROMPT）
- 意图分类（`src/agent/perception/intent.py`）：规则正则优先（greeting/clarification/chit_chat 等 7 类）→ 规则不中调 LLM 兜底 → 失败降级 general_query；结果注入模型上下文，闲聊意图跳过工具绑定省 token
- 流式：`astream_events` 提取 5 类事件（token/tool_start/tool_end/done/error），工具结束事件顺带提取 wiki 来源路径；流结束后结构化提取回答 + SQLite 持久化 + 建全文索引
- 工具：3 个只读工具（search_wiki / read_page / query_graph），经 ToolRegistry 管理（注册/启停/权限元数据/绑定模型）

**过程方法（为什么）**：
- **手写 StateGraph 而非 create_react_agent**：需要四段条件路由（意图分流/前置校验/审批/质检），标准循环给不了；且手写才理解 add_messages reducer、conditional_edges、interrupt/Command 机制
- **recursion_limit=150**：图每轮走 7-8 个节点，框架默认 25 只够约 3.5 轮，先于业务熔断触发；150 = 业务熔断 15 步 × 每步约 8 节点 × 1.25 余量，保证业务熔断永远先触发
- **审批是在图中间暂停而非事后审计**：interrupt 保存 checkpoint 停止执行流，resume 从中断点继续，状态不丢
- **只读工具起步**：工具越少越可控；未来加写工具只需注册时标 requires_approval=True，审批节点自动接管，路由层零改动

**踩坑**：
- **recursion_limit 默认 25 太小（第 4 轮对话崩溃）**
  - 现象：多轮对话跑到第 4 轮左右抛 GraphRecursionError，业务熔断（15 步）还没触发
  - 根因：recursion_limit 按 super-step（节点跳转）计数，本图每轮 7-8 个节点，25 只够约 3.5 轮；框架默认值先于业务设计值触发
  - 解决：显式设 recursion_limit=150（15×8×1.25），代码注释写明推导过程
  - 教训：框架默认值是给通用场景的，自定义循环必须重算这个数
- **Windows 事件循环阻塞（进程崩溃）**
  - 现象：SSE 流式对话在 Windows 上偶发整个进程卡死/崩溃，Linux 复现不出
  - 根因：LangChain `with_structured_output` 内部是同步 httpx 调用，在 async 事件循环里直接调用阻塞循环；Windows ProactorEventLoop 被阻塞后行为更糟
  - 解决：统一 `asyncio.to_thread()` 包同步 LLM 调用（结构化输出、意图分类）
  - 教训：同步网络调用混进 async 事件循环是必踩的坑，建立"所有同步调用必须 to_thread"的纪律
- **interrupt 挂起后状态机误用（脏状态）**
  - 现象：审批挂起期间收到新消息 / 前端没带审批决策就 resume → 状态错乱或报错
  - 根因：图在 approve 节点 interrupt() 暂停后只接受 Command(resume=approval)，不接受新消息；resume 必须有合法审批决策
  - 解决：入口 get_state 快照检测 interrupts，两道防御（没带审批 → 明确 error 事件；审批格式校验）；恢复时不传新消息
  - 教训：HITL 的严谨性在状态机——图是从中断点继续，不是从头跑
- **MemorySaver 同 thread 冲突（regenerate 串味）**
  - 现象：重新生成回答（regenerate）和原会话共用 thread_id，checkpoint 互相覆盖，结果串味
  - 根因：MemorySaver 按 config 的 thread_id 索引 checkpoint，regenerate 复用原 id 读写同一 checkpoint
  - 解决：regenerate 用独立 config 后缀（`{thread_id}_reg`），跑完单独持久化
  - 教训：checkpointer 的隔离单位是 config 不是会话
- **意图分类同步调用阻塞首 token**
  - 现象：意图分类在流式输出前同步执行，首次对话首 token 延迟高
  - 根因：同步实现混入 async（坑 2 变体）
  - 解决：asyncio.to_thread 包裹 + 失败降级不阻断（unknown 继续）
  - 教训：一个坑出现两次就要立纪律

**数据**：
- 无效工具调用降低约 60%：**开发期对比测试**（裸 ReAct vs 三层自纠错，同测试集对比工具调用次数；04 文档标注"开发期对比，未上生产"，补测清单要求面试前复跑）
- 平均回答延迟 / 首 token 延迟：**无相关数据**
- 自纠错触发率：**无相关数据**
- 测试覆盖：Agent 相关 pytest 用例数见"工程化"（未单独统计）

**证据**：`src/agent/planning/graph.py` · `src/agent/session.py` · `src/agent/action/registry.py` · `src/agent/action/tools.py` · `src/agent/perception/intent.py` · `src/agent/planning/prompt.py` · `interview/06-核心代码与逻辑.md` · `interview/08-Agent踩坑记录.md`

## 功能 5：记忆系统（双轨记忆 / 持久化 / 摘要）

**功能**：为多轮对话提供两类记忆：用户驱动的 Attention Sink（长记忆）+ 系统驱动的 Working Memory（任务态），配合 SQLite 持久化（重启恢复）与 LLM 摘要压缩（上下文长度控制）、会话全文检索。

**如何实现（是什么）**：
- Attention Sink（`src/agent/memory/attention.py`）：显式锚定（"记住 XX"检测）+ 高频实体自动锚定（≥3 次出现）；每轮置信度衰减 0.05，<0.3 或闲置 >20 轮淘汰；容量 ≤15 个，按置信度降序
- Working Memory（`src/agent/planning/graph.py` 的 working_memory_reducer）：5 槽位（用户身份/当前目标/关键事实/工具缓存/提及实体），按槽位策略合并——事实/实体 dedup 追加 + 上限截断、工具缓存最新覆盖、身份 key 级合并
- 摘要压缩（`src/agent/memory/summarizer.py`）：>40 条非系统消息触发；独立小模型（与主模型分开配额）；返回 RemoveMessage 列表 + 摘要 SystemMessage；过滤 ToolMessage 噪声；摘要时注入 sink + WM 上下文保证关键信息跨摘要存活
- 持久化（`src/agent/memory/store.py`）：MemorySaver 管运行时 checkpoint，SQLite 管会话消息/记忆回灌；冷启动反序列化回灌消息 + sinks + WM；30 天闲置会话归档降级（LLM 生成归档摘要）
- 全文检索：SQLite FTS5 + CJK 检测降级 LIKE 模糊匹配

**过程方法（为什么）**：
- **双轨而非单轨**：用户驱动的记忆回答"用户在意什么"（要记住），系统驱动的记忆回答"任务进行到哪"（当前状态）；两类需求合并会互相污染
- **置信度衰减**：模拟"记忆会淡忘"——不复习就衰减，不是永久存储；衰减按轮次计数，与摘要不冲突
- **摘要独立模型**：不挤占主对话 token 配额，压缩成本可预期
- **FTS5 中文降级而非 jieba**：FTS5 自定义 tokenizer 在 Python 集成成本高，LIKE 对个人项目数据量够用——成本收益取舍

**踩坑**：
- **FTS5 对中文匹配差**
  - 现象：对话全文搜索搜中文关键词命中率低，搜英文正常
  - 根因：FTS5 默认分词按空格/标点切词，中文无空格，整句一个 token，子串匹配不上
  - 解决：查询侧分流——含 CJK 走 LIKE 模糊匹配，纯英文走 FTS5 MATCH
  - 教训：中文检索不能直接套英文分词假设；评估过 jieba，成本收益不合算所以没上
- **旧摘要残留（已知 P3 bug）**
  - 现象：摘要压缩后，被 RemoveMessage 标记删除的旧消息在部分场景仍出现在上下文，摘要重复注入
  - 根因：summarizer 返回 RemoveMessage + 摘要，但某些分支（reflect_node 修正后重入）的消息列表状态没同步清理
  - 解决：定级 P3 低优记录在案（触发路径窄：反思重入 + 摘要同轮），当时未修
  - 教训：不是所有 bug 都要立刻修，分级决策本身是工程能力；讲坑时先说"已知边界 case"

**数据**：
- 摘要触发阈值：40 条非系统消息（实现常量）
- sink 参数：衰减 0.05/轮、淘汰 <0.3、闲置 >20 轮、容量 15（实现常量）
- 压缩前后上下文长度对比：**无相关数据**
- 记忆命中率 / 遗忘正确率：**无相关数据**

**证据**：`src/agent/memory/attention.py` · `src/agent/memory/store.py` · `src/agent/memory/summarizer.py` · `src/agent/planning/graph.py`（reducer）· `interview/08`（坑 5/6）

## 功能 6：安全与权限

**功能**：四层安全——路径安全（防穿越）、目录隔离（raw 只读/wiki 可写）、LLM 输出校验（防脚本注入）、页面访问控制（密码门禁 + 隐私标记）。

**如何实现（是什么）**：
- 路径安全：`src/tools/path_utils.py` 的 `safe_path()` 统一校验——拒绝绝对路径、规范化后校验最终路径仍在前缀内（防 `../` 穿越）；工具层与 API 路由共用同一真源
- 目录隔离：raw/ 只读（任何 Agent 不能修改）、wiki/ 可写（LLM 维护）、src/ 与 .claude/ 只读（人类维护）
- LLM 输出校验：写入前校验文件名（不能含 `../` 或空路径）、Markdown 不允许嵌入 `<script>`/`<iframe>`、页面类型必须在白名单（entity/concept/source/query 等）
- 访问控制：页面密码验证（bcrypt 哈希，`src/core/auth.py`）；隐私标记（frontmatter privacy 字段）——生成时全量生成，restricted 页面按标记门禁展示
- 审计：`operation_log` 表记录写操作（add_page/add_link 等）

**过程方法（为什么）**：
- **路径安全收敛唯一真源**：工具和路由各写校验会漏（防穿越必须统一），单一真源保证改一处全局生效
- **隐私"生成全量 + 按标记门禁"而非生成时过滤**：知识价值不因隐私降低，只限制谁能看——对比"直接不生成"，避免知识缺口
- **raw 只读是信任边界**：raw/ 是事实基准，wiki 任何问题都能从 raw 重建

**踩坑**：无独立踩坑条目（安全体系的设计迭代未记录专项坑；相关教训见经验汇总"LLM 生成输出不可信 → 源头硬约束"）。

**数据**：
- 路径穿越拦截次数：**无相关数据**
- 密码保护页面数：**无相关数据**
- 隐私标记页面数：**无相关数据**

## 功能 7：前端（React SPA / SSE 流式）

**功能**：React 19 单页应用，九页面：Chat（对话，SSE 流式渲染）/ Wiki（知识库浏览，左侧目录树 + 右侧阅读）/ 原始资料 / 检索（三模式切换）/ 图谱（可视化）/ Wiki 检查（Audit）/ 设置（LLM/界面/向量开关等）/ 首页。与后端 /v1/ API 对接。

**如何实现（是什么）**：
- 技术：React 19 + Vite + TypeScript + Tailwind CSS 4 + HeroUI（组件库）
- 对话页：SSE 逐 token 渲染，处理 5 类事件（token/tool_start/tool_end/done/error），工具调用过程实时展示，审批挂起弹确认
- Wiki 页：左侧目录树（wiki/raw 双 tab，自动定位当前文件）+ 右侧阅读区（元数据卡片 + Markdown 渲染 + wikilink 跳转 + 编辑）
- 检索页：BM25/向量/混合三态切换，结果分页
- 设置页：LLM 模型配置、界面主题（浅色/深色/跟随系统）、向量搜索开关等，持久化到本地 + 后端
- 状态管理：React hooks + fetch（API 调用封装），无重型状态库

**过程方法（为什么）**：
- **React 而非服务端模板**：早期用 Jinja2 模板方案评估后放弃——交互密集（流式渲染/图谱可视化）需要 SPA
- **SSE 而非 WebSocket**：单向流式输出场景 SSE 更简单（HTTP 原生支持、自动重连语义），不需要双向通道
- **组件库选 HeroUI**：基于 Tailwind v4，主题变量（浅/深色）全局切换，避免手写大量样式

**踩坑**：
- **HeroUI v3 CSS 分层导入导致组件无样式**（本会话修复）
  - 现象：Card 等组件渲染出来无背景/边框/圆角（计算样式全为 0）
  - 根因：按 v2 方式分层导入 `@heroui/styles/base` 等，v3 要求单行 `@import "@heroui/styles"`，CSS layers 优先级导致样式被清零
  - 解决：index.css 改为单行导入
  - 教训：组件库升级要查迁移文档的 CSS 导入方式，不能用旧版本姿势

**数据**：
- 前端测试：81 个（实测，pnpm test）
- 首屏加载 / 流式渲染延迟：**无相关数据**
- 浏览器兼容测试：**无相关数据**

## 功能 9：工程化（测试 / 打包 / 部署）

**功能**：测试体系（后端 pytest + 前端 + E2E）、桌面打包（PyInstaller 单文件）、数据持久化（SQLite 16 表 + 参数化查询）、部署（GitHub Actions workflow + 最小依赖清单）。

**如何实现（是什么）**：

- 打包：PyInstaller 单文件 exe，`run.py` 入口（单实例锁 + 崩溃兜底）
- 数据库：SQLite 16 表（wiki_pages/page_links/operation_log/ingest_cache/privacy_rules/token_usage_log/model_pricing/graph_relevance/wiki_settings/lint_cache/ingest_queue 等），全部参数化查询，写操作即时 commit
- 部署：GitHub Actions workflow（push main 触发），requirements-min.txt 最小依赖清单（补充过 python-multipart 表单上传必需依赖）

**过程方法（为什么）**：
- **LLM 全 mock**：测试不实际调 API，可重复可离线
- **最小依赖清单**：面向部署体积，可选重依赖（torch 等）延迟 import，兼容最小部署集
- **参数化查询**：禁止字符串拼接 SQL（防注入，安全规则文档明确）

**踩坑**：
- **SQLite 跨线程报错**
  - 现象：多线程请求下报"SQLite objects created in a thread can only be used in that same thread"
  - 根因：SQLite 默认连接绑线程，Agent 层多线程调用触发
  - 解决：模块级单例连接 + check_same_thread=False，写操作即时 commit
  - 教训：并发写靠 SQLite 自身锁 + 短事务，个人项目量级够用且简单
- **requirements-min.txt 漏 python-multipart**
  - 现象：/v1/ingest/upload 表单上传返回 400
  - 根因：官方最小清单遗漏 FastAPI 表单上传必需依赖
  - 解决：补充 python-multipart
  - 教训：最小依赖清单要按实际功能路径核对，不能只抄官方示例
