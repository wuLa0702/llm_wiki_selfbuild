## 1. 项目定位与一句话

**一句话**：基于 LangGraph 单 Agent 的 **wiki 语义化存储系统**——把非结构化资料编译成互链的结构化 wiki 页面（而非塞进向量库），Agent 在 wiki 上问答，WikiGraph 图关系提供语义关联。**核心差异化：不做 RAG，做 wiki。**

**技术栈故事线**：手写 LangGraph StateGraph（10 节点）→ 两步 CoT 编译 → wikilinks + WikiGraph 图 → 三角定位查询 → HITL 审批 → 自修正三层 → 打包部署。

| 追问 | 预演答案 |

## 3. wiki 存储 vs RAG 决策故事（必考题）

> **讲法：先讲 RAG 的坑（为什么不用），再讲 wiki 怎么做，最后主动讲代价。**

**① 为什么不做 RAG**：
1. **chunk 碎片化**：文档切块后检索片段，答非所问——丢了标题/章节/上下文
2. **黑盒相似度**：向量 top-k 结果无法解释，错都不知道为什么
3. **依赖重**：embedding 模型（sentence-transformers）~2GB 内存，云服务器扛不住（实测）

**② 所以改成 wiki 语义化**：
```
文档 → 两步 CoT 编译 → wiki 页面（标题/分类/互链）
  → WikiGraph（wikilinks → 4-Signal → 社区）
  → 三角定位查询（SQLite + BM25 + 图扩展 + index.md 兜底）
```

**③ 代价主动讲**：
- 编译耗时：两步 CoT 每页两次 LLM 调用，大批量导入慢 → 用 SHA256 缓存 + 队列异步
- 编译质量依赖 LLM：生成页面可能不完整 → 用 verify_result 校验 + lint 检查兜底
- 图构建：确定性算法快但依赖 wikilinks 质量 → 4-Signal 多信号加权

**④ 什么时候该用 RAG（反问展示深度）**：实时/流式知识、大规模文档库、检索是核心的场景用 RAG 合理；wiki 适合"要沉淀、要整理、要语义关联"的知识库。

## 4. 核心功能 STAR 故事库

### 故事 1：wiki 语义化存储（最亮）
**S**：人人做 RAG，检索碎片答非所问；个人知识库需要"可整理、可关联"
**T**：把文档编译成 wiki 而非塞向量库
**A**：两步 CoT 编译（分析→生成）→ wikilinks 互链 → WikiGraph 图 → 三角定位查询
**R**：**非向量也答准**——SQLite+BM25+图扩展+index 兜底；782 测试覆盖

### 故事 2：手写 StateGraph（工程深度）
**S**：最初模型行为不可控（工具调用/上下文管理靠 prompt 不稳）
**T**：用 LangGraph StateGraph 把 Agent 行为工程化
**A**：手写 10 节点（intent→推理→记忆→审批→工具→自修正）+ MemorySaver 落库
**R**：每步可观测、可中断、可恢复；三层自修正兜底工具/结果/推理

### 故事 3：语义搜索关闭（工程取舍，bad case 反转）
**S**：想加语义搜索，embedding 依赖太重（~2GB 内存，云服务器扛不住）
**T**：最小依赖可部署
**A**：关闭向量、降级 BM25、保留开关结构（chromadb 注释 + 启用步骤文档化）
**R**：**"不盲目上依赖，够用就好"**——默认 BM25 够答准，向量是可选增强
