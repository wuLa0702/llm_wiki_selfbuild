## §1 总（30s）

> "核心卖点是**存储方案的选择**：我不用烂大街的 RAG（文档塞向量库、top-k 检索），而是把文档**编译成互链的结构化 wiki 页面**，查询用三角定位（SQLite + BM25 + 图扩展 + LLM 兜底）。收益：语义上下文保留、可编辑、可审计，还多出 WikiGraph 图关系这个 RAG 没有的维度。"

## §2 分（60-90s）

**① 为什么不做 RAG**：
- chunk 碎片化 → 检索片段答非所问；相似度 top-k 是黑盒，错了无法解释
- 文档变 chunk 后丢失标题/章节/上下文结构

**② wiki 存储怎么做**：
- 两步 CoT 编译：Step1 结构化分析 → Step2 LLM 生成 wiki 页面（带标题/分类/互链）
- 页面间 `[[wikilinks]]` 显式互链 → WikiGraph 图关系（4-Signal 关联度 + Louvain 社区）

**③ 查询三角定位**（不依赖向量也答准）：
- SQLite 全文 + SearchTool BM25 + WikiGraph 邻居图扩展 + LLM 读 index.md 兜底
- 追问点：「为什么加图扩展？」→ 全文检索答不出"哪些页面主题相关"，图关系弥补语义

## §3 流程图

```
文档 → 两步 CoT 编译 → wiki 页面（互链）
  → WikiGraph（wikilinks→关联度→社区）
  → 查询：SQLite + BM25 + 图扩展 + index.md 兜底 → LLM 综合 → 回答
```

## §4 总（20s）

> "这不是炫技，是**存储哲学的选择**：向量库存相似度，wiki 存语义结构。文档编译成 wiki 后，可读、可编辑、可审计，还多出图关系回答'哪些相关'。面试官问 RAG 相关，我能从对比讲到取舍。"
