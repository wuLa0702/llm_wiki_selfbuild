## §1 总（30s）

> "查询不做向量 top-k，而是**三角定位**：SQLite 全文 + BM25 检索 + WikiGraph 图邻居扩展 + LLM 读 index.md 兜底，四路命中页面组装上下文给 LLM 综合。不依赖向量库也答得准，还支持最小依赖部署。"

## §2 分（60-90s）

**① 四路定位**：
- SQLite 全文（`search_pages`）+ SearchTool BM25 → 关键词命中
- WikiGraph 邻居扩展 → 语义相关页面（图关系兜底）
- LLM 读 `index.md`（导航页）→ 全局兜底（全文检索不到的）

**② 为什么不用向量检索**：
- 向量库（Chroma + embedding 模型）是重依赖，语义搜索当前版本关闭（去依赖 + 降级 BM25）
- 三角定位够答准——wiki 页面本身有语义结构，不需要向量相似度

**③ 上下文组装**：命中页面 → 按相关度裁剪 → 组装 prompt → LLM 综合 → 可选归档查询

## §3 流程图

```
用户问题 → QueryEngine
  → SQLite 全文（关键词）→ 命中页
  → BM25（CJK 分词）→ 命中页
  → WikiGraph 邻居扩展（语义相关）→ 相关页
  → LLM 读 index.md（全局兜底）
  → 四路命中合并 → 上下文裁剪 → LLM 综合 → 回答（可归档 wiki/queries/）
```

## §4 总（20s）

> "三角定位是**工程取舍**：不为向量检索的'酷'买单，用 wiki 本身的结构把查询做扎实。默认 BM25、向量可选，最小依赖可部署——这是我从'能跑'到'可交付'的思考。"
